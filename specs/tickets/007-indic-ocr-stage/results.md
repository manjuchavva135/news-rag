## indic-ocr on vLLM (departure from FR-1, FR-2, D-3)

The ticket asked for indic-ocr in its own venv as a stdin/stdout worker on its transformers
recognizer (`HfRecognizer`). That was built first and ran correctly, but far too slowly:

| Setup (same pages) | pages/s |
|--------------------|---------|
| transformers worker as the ticket describes, first dev-sample run | 0.04 |
| + tokenizer fix + per-block token budget, one page at a time | 0.07 |
| + blocks of 3 pages batched together | 0.13 |
| vLLM 0.33 (envs/vllm), blocks of 3 pages in flight | 1.15 (text step only) |
| **final stage on vLLM, 20-page dev sample** | **0.96** |

transformers decodes about 40 ms per step whatever the batch size, and a long article block
needs ~430 tokens; indic-ocr's own code calls `HfRecognizer` the slow quick-start path. With
the user's agreement the text model now runs on vLLM 0.33 from `envs/vllm` (ticket 006),
started under the stage's GPU lock, so `envs/indic-ocr/` and `indic_worker.py` were dropped.
On 3 pages the vLLM text matches the fixed transformers text (median similarity 1.000 over
79 text blocks; small differences in one table and one header, as indic-ocr's docs expect
between backends).

Crops and prompts follow indic-ocr's recipe (box clamped to the page, area scaled into
256²..1536², its transcription prompt and its HTML table prompt); `ocr install` refuses to go
on if the pinned snapshot's prompts differ from ours.

## Problems found while testing, and fixes

- **Wrong tokenizer (both transformers and vLLM).** For `model_type: qwen3_5`, transformers
  (5.20 in envs/vllm, 5.22 in the old indic venv) ignores the snapshot's `tokenizer.json` and
  loads its byte-level Qwen tokenizer. Prompts were mis-encoded (a short Telugu sentence became
  67-76 tokens instead of 13-21) and the output kept U+2581 instead of spaces (2,426 in one
  vLLM test on 3 pages). Fix: vLLM gets `--tokenizer` pointing at a folder with only
  indic-ocr's tokenizer files and no `config.json`, so transformers keeps `tokenizer.json`
  as it is. `ocr install` checks the exact round trip in envs/vllm.
- **Tiny boxes ran to the token limit.** Small PageFooter boxes (~150x70 px, likely icons or
  QR codes) are read as LaTeX (`$$ \text{---} \text{---} …`) until `max_tokens`. Each text
  block now gets a budget of `ocr_tokens_per_mpx` = 1500 tokens per megapixel of its crop
  (real text needs at most ~560), at least 96; tables keep 2048. On 3 pages real article text
  was unchanged by the budget.
- **Running downloaded code was blocked at first** by auto mode (indic-ocr's `install.sh` and
  its Python code from the Hub); the user allowed it. Neither runs any more: the snapshot's
  code is only read (with `ast`) and its weights are served by vLLM.

## Surya 0.23 (where I read the spec a particular way)

- The newest surya-ocr (0.23.0) made its main `LayoutPredictor` a VLM (surya-ocr-2.5) that
  needs a vLLM server (Docker by default) and most of the GPU. It also ships
  `surya.fast_layout`: an rf-detr layout detector with a learned reading-order head
  (`datalab-to/surya_layout2`, 448 px input), with a confidence per box. The worker uses that
  detector (`LayoutEngine`, in-process, on the GPU, 1.5 GB). It is small enough to sit beside
  the text model (D-8) and gives per-box confidences. One confidence per page is all the VLM
  path offers. About 0.3-1.5 s per page.
- Its boxes come back in pixels of the 300 DPI PNG; the stage still scales them if a worker
  reports another size.

## Notes and known issues

- **Footer junk:** those small PageFooter boxes still produce ~100-300 characters of LaTeX
  junk each (bounded by the budget). They are `header_footer` blocks; ticket 009's sanity check
  or 011's folio reading should drop them.
- `unknown_labels` in the detail is a count. `ocr show` with no `--stage` picks the first done
  of `ocr_final`, `ocr_split`, `ocr`.
- vLLM takes ~2 minutes to start (compile + CUDA graphs, cached under `~/.cache/vllm`); the
  `excl. model load` line measures wall clock from the first page start to the last page end.
- In this run all 20 dev-sample pages were processed under the new version; the first run's
  artifacts (old version, broken tokenizer) were deleted from `/home/admin1/raw/work/ocr/`.
  Their logs are kept as `evidence/superseded-*.log`.
